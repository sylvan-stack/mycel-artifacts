# Guide: Nex Colab

Use this guide when the owner asks to learn something with `/colab "prompt"`,
or asks that their knowledge be taken into account in other work with
`(use colab)`. The agent answers at the depth the owner's
[Nex Knowledge Map](../../arbol/GLOSSARY.md#nex-knowledge-map) says is
missing, logs every time it shows the owner something, judges from the
owner's own words whether a level has risen or fallen, and writes the map
and the log, then commits and pushes them, after each reply of the owner's.
[Nex Colab](../../arbol/GLOSSARY.md#nex-colab) is that exchange: the owner
is its [H-Nex](../../arbol/GLOSSARY.md#h-nex), the agent an
[A-Nex](../../arbol/GLOSSARY.md#a-nex).

This guide is authoritative for the steps an agent takes and the lines it
says, in Claude Code, in Codex and in an Arbol chat; an agent needs this
guide alone. What the steps must achieve, and why, is in the specifications
of the private corpus `~/Artifacts/colab/`:
[CLB-0](../../colab/specs/00-the-nex-knowledge-map.md), the map and the log;
[CLB-1](../../colab/specs/01-nex-colab.md), the exchange and `(use colab)`;
[CLB-2](../../colab/specs/02-showup.md), showup. Read them for a reason, not
for a step. The guide reads and writes the map as data, with the check that
lives in that corpus.

**Contents:** when to use · the corpus and its files · an exchange, round by
round · writing the map and the log · (use colab) · showup · the lines the
owner sees · what the agent never does · not built yet.

## When to use

| The owner writes | It starts | Section |
|---|---|---|
| `/colab "<prompt>"`; in Codex `$colab "<prompt>"` | an exchange | [An exchange, round by round](#an-exchange-round-by-round) |
| `/colab showup "<words>"`; in Codex `$colab showup "<words>"` | a showup: the owner states their own level | [showup](#showup) |
| `(use colab)` anywhere in a message, or `/use-colab <message>`; in Codex `$use-colab <message>` | the map used in that work | [(use colab)](#use-colab-the-map-in-other-work) |

Nothing else starts either. A question that only looks like a learning
question, "what is a CRDT?", gets an ordinary answer, and a message without
the phrase `(use colab)` neither reads nor writes the map. The skill `colab`
starts on its two forms only, the first word `showup` choosing the second;
the skill `use-colab` starts on the phrase and on its own name only. Both
hand this guide the whole message.

## The corpus and its files

The corpus is the folder that the variable `COLAB_CORPUS` names when it is
set, and `~/Artifacts/colab/` when it is not. A sample sets it to point the
agent at a fictional corpus; the owner never does. Find it once per session:

```bash
printf '%s\n' "${COLAB_CORPUS:-$HOME/Artifacts/colab}"
```

Below, `<corpus>` is the folder this prints.

**The corpus is private**, because the map describes the owner. Its levels
are quoted to the owner in the session and nowhere else: nothing of `map/`
or `log/` goes into a reply outside the owner's session, another corpus, a
specification, a Linear page or a sample's fixtures. Every note, evidence and
`shown` speaks of the owner's learning in general terms and never names a
repository, a project or a product, the owner's own included, also when the
prompt was about one ([CLB-0, Privacy](../../colab/specs/00-the-nex-knowledge-map.md#privacy)).

| File | What it is |
|---|---|
| `map/INDEX.md` | Every topic on one line, nested as the tree is: its title linked to its file, its level or `not assessed`, and `also:` with its aliases; then `## Not interested` with the paths of the marked topics. Generated by `index`; never edited by hand |
| `map/<path>/topic.md` | One topic. Its folder's path from `map/` is its identifier, such as `software-development/postgresql/advisory-locks`; the folders inside it are its children |
| `log/<YYYY-MM>.jsonl` | The learning log of one UTC month, one JSON object per line, appended and never changed |

### A topic's file

A key block between two lines of `---`, then the body. Fictional example:

```
---
title: Advisory locks in PostgreSQL
level: superficial
aliases:
  - advisory locks
entries:
  - level: superficial
    source: agent
    date: 2026-10-21
    evidence: "exchange on advisory locks, claude-code session <session>; test of superficial met: took a lock inside a transaction and expected it to stay, which shows what the lock is for"
related:
  - software-development/postgresql/transactions
gaps:
  - lock timeouts
---
# Advisory locks in PostgreSQL

The two scopes, session and transaction, were new; the example of a
pooled connection worked.
```

| Key | When | What |
|---|---|---|
| `title` | always | The full name, in a few words |
| `level` | when there are entries | The newest entry's level; absent without entries |
| `aliases` | optional | Other names a prompt may use |
| `entries` | optional | Newest first; each with `level`, `source` (`owner` or `agent`), `date` (`YYYY-MM-DD`, UTC) and `evidence` |
| `related` | optional | Paths of related topics; each link written in both topics |
| `gaps` | optional | Parts of the topic not learned yet, a few words each |
| `former` | optional | Paths the topic had before the owner moved it |
| `not-interested` | optional | `true`: the owner does not want to learn this topic or anything under it. Set and removed on the owner's word only |

The block is a small subset of YAML, and `check` reports anything else: one
`key: value` per line; a list as `key:` followed by lines `  - item`; an
entry as `  - level: …` followed by `    source: …`, `    date: …` and
`    evidence: …`; a value in double quotes when it holds `:` or `#`, with
`\"` and `\\` as the only escapes; `not-interested: true` never quoted; no
comment, no blank line, no tab, no `[a, b]` list and no value over several
lines. The level is one of *ignorant*, *superficial*, *practical*,
*advanced* and *design*. The body holds the notes for pitching an answer:
what the owner knows the topic through, what confused them, which examples
worked. `index` writes a section `## Children` at the end of the body when
the topic has children; nothing is written below it by hand. The folder's
name is lower-case ASCII letters and digits, words joined by hyphens, and
every folder under `map/` holds a `topic.md`. The full form is
[CLB-0's Interface](../../colab/specs/00-the-nex-knowledge-map.md#interface).

### A log line

One JSON object on one line, with exactly the keys of its kind. Every line
has `at` (UTC, `2026-10-21T09:14:02Z`), `kind`, `session` and `topics` (the
paths it is about). An exchange writes three kinds; the fourth, `statement`,
is showup's.

| Kind | When | Its own keys |
|---|---|---|
| `added` | a topic is added to the map | `reason`: why, one sentence |
| `attempt` | a reply showed the owner something | `shown`: what, one or two sentences; `before`: path → level of each topic shown, a topic without entries left out |
| `assessment` | a level changed | `before`: path → level, a topic without entries left out; `level`: path → the new level; `evidence`: the test met |

Fictional example, one round that added a topic, showed it and raised it:

```
{"at":"2026-10-21T09:14:01Z","kind":"added","session":"claude-code <session>","topics":["software-development/postgresql/advisory-locks"],"reason":"needed for a question on why an advisory lock is gone after commit"}
{"at":"2026-10-21T09:14:02Z","kind":"attempt","session":"claude-code <session>","topics":["software-development/postgresql/advisory-locks"],"shown":"the two scopes of an advisory lock, session and transaction, when each fits, and that a transaction-level lock is released at commit","before":{}}
{"at":"2026-10-21T09:14:03Z","kind":"assessment","session":"claude-code <session>","topics":["software-development/postgresql/advisory-locks"],"before":{},"level":{"software-development/postgresql/advisory-locks":"superficial"},"evidence":"test of superficial met: took a lock inside a transaction and expected it to stay, which shows what the lock is for"}
```

The full form is
[CLB-0's Interface](../../colab/specs/00-the-nex-knowledge-map.md#interface).

### The session

`session`, in every log line and in the evidence of an entry, names the tool
and the session the agent runs in:

| The agent runs in | `session` | Where the identifier is |
|---|---|---|
| Claude Code | `claude-code <session id>` | the variable `CLAUDE_CODE_SESSION_ID` |
| Codex | `codex <thread id>` | the variable `CODEX_THREAD_ID` |
| An Arbol chat | the chat's [Entity URI](../../arbol/GLOSSARY.md#entity-uri) | given to the agent with the chat |

### The commands

The check of the map is `~/Artifacts/colab/tools/knowledge_map.py`, Python's
standard library only. It works on the folder it is started in, so it is run
from the corpus, whichever corpus that is:

```bash
cd "<corpus>" && python3 ~/Artifacts/colab/tools/knowledge_map.py index
cd "<corpus>" && python3 ~/Artifacts/colab/tools/knowledge_map.py check
```

- **`index`** regenerates `map/INDEX.md` and every topic's `## Children`
  section, prints `wrote <file>` for each file it changed, and changes nothing
  else. When a topic has an error other than an out-of-date summary, it
  writes nothing, lists the errors and exits 1.
- **`check`** prints one line `<file>: <message>` for each file of `map/` and
  `log/` that is out of form, sorted by file, and exits 1; it prints nothing
  and exits 0 when the corpus is in form. It checks the form of the files and
  knows nothing of levels.

Git: the corpus is committed and pushed only when it is a git repository of
its own, `git -C "<corpus>" rev-parse --show-toplevel` printing `<corpus>`,
with the identity git already has and no agent credit.

## An exchange, round by round

An exchange is made of *rounds*: one message of the owner's and the agent's
reply to it. The first round's message is `/colab "<prompt>"`. A later
message is a round when it stays on the exchange's topics: one number from
the last list of options, an objection to the last skipped line, or a
question or a statement about a topic the exchange has touched. A number
that is not on the list gets one question back. Any other message ends the
exchange, without a word said: thanks, other work, another
`/colab "<prompt>"`, which starts a new exchange, or the session closing. An
owner who comes back to a topic the next day starts a new exchange; the log
ties the two by the topic's path.

Two kinds of message neither end the exchange nor are rounds:

- **A showup in the middle**, `/colab showup "<words>"`. Its message, its
  question and every message that answers the question, up to the showup's
  reply, belong to the showup: they show nothing, write no `attempt` line and
  no skipped line, and are no evidence for the exchange's assessment. The
  agent records it as [showup](#showup) says, then goes on with the exchange:
  it reads the files of the topics the showup changed again, pitches what it
  shows next at the new level, and says in one line what it now skips. What
  it shows after the showup, in the same reply or the next, is a round. A
  mark set on the topic being explained ends that explanation. Words that
  name no topic, `/colab showup "advanced in this"`, refer to the topics of
  the exchange's last `attempt` line.
- **A request in plain words to record a level**, "note that I know this
  well". The reply begins with the `To record it:` line, and nothing is
  written for it.

The agent cannot see a session end, so it treats every round as possibly the
last: everything a round changed is in the map, in the log and pushed before
its reply is given.

**The first round** takes seven steps:

1. [The prompt](#step-1-the-prompt): is it a Nex Colab prompt, and what is
   its general topic?
2. [The topics](#step-2-the-topics): the topics the prompt touches and the
   topics the answer needs, found in the map, read, and set aside when the
   owner is not interested in them.
3. [The depth](#step-3-the-depth): topic by topic, what is skipped and what
   is explained, at which level.
4. [The reply](#step-4-the-reply): the explanation, the skipped line, and
   the ways deeper as numbered options last.
5. [The `attempt` line](#step-5-the-attempt-line) for what the reply shows.
6. [The assessment](#step-6-the-assessment): from the owner's words in the
   exchange so far, whether a level has risen or fallen, over every topic the
   exchange has touched.
7. [Writing the map and the log](#step-7-writing-the-map-and-the-log):
   the files, `index`, `check`, the commit and the push.

**Every later round** takes steps 3 to 7 for what its message asks. A number
picks an option: the round explains that way, pitched at the level the option
named. A question is answered at the owner's depth, and is the evidence step
6 reads. An objection to the skipped line is answered by explaining what was
skipped, or by moving the pitch up, as step 3 says. An answer that says the
owner is done, or that is other work, ends the exchange.

Nothing is written before step 7, and every `before` is the level a topic
showed at the start of the round. Steps 4 to 6 prepare the reply; it is
given once step 7 is done, so that its lines say what was written.

### Step 1: the prompt

The prompt is what the owner wants to learn, in their own words.

- **A question in general**, "what is a CRDT?", "advisory locks": the topics
  are in the words.
- **A question about something in the current session**, "why did you use a
  fixture in the test you just wrote?": name the general topic behind the
  thing, test fixtures, and explain that topic at the owner's depth with the
  thing in the session as its example. The map and the log record the
  general topic only, in general terms: "asked why a test needs a fixture",
  never what the test or its repository is.
- **No general topic behind it**, "what does this project's `retry` setting
  do?": the test is whether someone could learn it from public sources,
  without access to a particular repository, project or product. When not,
  it is no Nex Colab prompt: answer it as without Nex Colab, write nothing
  to the map or the log, and begin the reply with the `Not a map topic:`
  line. A prompt that mixes the two, "why does this project's retry loop use
  exponential backoff?", is a Nex Colab prompt about its general topic,
  exponential backoff.

The prompt need not name a level: the map supplies it. Words that *use* a
topic, "I took the lock inside the transaction and expected it to stay", are
evidence that step 6 reads. Words that only *claim* a level, "I use
transactions every day" or "I am new to this", meet no test by themselves:
pitch the round at the level they name, say so in the skipped line, and
write no entry for the claim alone. A claim not to know a topic is the one
exception: it is evidence for lowering the level shown (step 6). A claim
becomes the owner's own entry only through a showup.

### Step 2: the topics

Run `index`, then read `map/INDEX.md` once. Match the subjects of the prompt
against the titles, the aliases and the paths, and decide two sets before
writing a word of the explanation:

- **The topics the prompt touches**: what the owner asks about, the subjects
  in its words or the general topic behind the thing in the session.
- **The topics the answer needs**: what an explanation of the touched
  topics, at the depth it will be pitched, rests on and cannot do without. In
  "why is my advisory lock gone after commit?", transactions, because a lock
  gone at commit cannot be explained to someone who does not know what a
  commit ends. A topic the explanation could mention but does not need is in
  neither set; it may be a way deeper.

Read the `topic.md` of every topic in both sets, and no other: its level,
its entries, its gaps and its notes, which say what confused the owner
before and which examples worked. Read the log lines that name its path, or
one of its `former` paths, since its newest entry (step 6 says which those
are): what was shown before is not shown again the same way.

- **A topic found under another parent, or under one of its aliases**, is
  used; it is never created a second time.
- **A topic with no entry** is *not assessed*: unknown, never *ignorant*.
- **A topic the map lacks** is noted. Step 7 adds it, but only when the round
  explains or assesses it, not when it is only skipped. It goes under the
  parent you judge right from the field the prompt belongs to and the topics
  already there, or as a new field at the top of `map/`, with every folder on
  the way. Prefer a shallow tree: `software-development/postgresql/advisory-locks`,
  not a chain of folders made for one topic. The map started empty, so an
  agent that finds nothing for a prompt is in the normal case.
- **A topic the owner is not interested in**, marked `not-interested: true`
  in its own file or in an ancestor's, is outside the map. `map/INDEX.md`
  lists marked topics by path only, under `## Not interested`: before
  matching, read the `topic.md` of each listed path in the prompt's field,
  for its title and aliases. When the prompt touches one, begin the reply
  with the `Not interested:` line and answer it plainly, at whatever depth
  the question needs, as any agent would. For that topic and everything under
  it, write no entry, gap, alias or log line, create no topic, pitch no
  explanation, offer no way deeper and follow no related link. A needed topic
  that is marked is used plainly and recorded nowhere. The other topics of
  the prompt are handled as usual. The mark is set and removed on the
  owner's word only, through showup or by hand, never on the agent's
  judgement.

### Step 3: the depth

The depth is decided topic by topic, for every topic the prompt touches and
every topic the answer needs, by the level the map shows. The rule is one
level up: the explanation gives what the test of the next level names, and
no more.

| The map shows | The explanation gives | So that the owner can, afterwards… |
|---|---|---|
| *ignorant*, or no entry and nothing in the prompt's words | what the topic is for and roughly how it works, in a few sentences, with one example | explain the idea in a few sentences |
| *superficial* | how to carry out the routine task: the steps, the common cases and the common mistakes, and where its documentation is | carry out a routine task with it alone |
| *practical* | how it works inside, its limits and its trade-offs, the alternatives and when not to use it | explain why it behaves as it does, and say when not to use it |
| *advanced* | how one would build it, with its trade-offs | lay out how one would build it |
| *design* | nothing more of the topic in general; a precise question is still answered, and the way deeper is a child, a gap or a related topic, which the reply says | — |

- **The pitch** rests on the level the topic shows, or on the higher level
  that the prompt's own words meet by the tests of step 6: a prompt that
  reasons about the inside of a topic the map has at *ignorant* is answered
  at the depth its words show, and step 6 brings the map up in the same
  round.
- **A precise question**, "how does the lock table work inside?", is
  answered at the depth it asks, whatever the level; the table pitches what
  the answer needs around it.
- **A touched topic with no entry**, and nothing in the prompt's words: pitch
  it for someone who does not know what it is for, write no entry, and say
  so in the skipped line.
- **A needed topic** is *skipped*, used without being explained, when the map
  has it at the level the explanation needs the owner to have in it, or
  higher. One the map has below that level is explained too, in the fewest
  words that let the explanation stand, pitched by the table, and offered as
  a way deeper of its own. One with no entry, or not in the map, is skipped
  and named in the skipped line as `not assessed`, so that the owner objects
  when they need it. Skipping writes nothing.
- **The notes** steer the wording: the example that worked before is reused,
  the one that confused is not, and one the log shows was shown before is not
  shown again.
- **An objection** to the skipped line is answered in the next round.
  "Explain transactions too": explain what was skipped. "I know advisory
  locks, go on" or "I am not new to CRDTs": a claim, so go on at the level
  the owner names; writing it into the map is the owner's showup.

### Step 4: the reply

The reply holds its lines in the order of
[The lines the owner sees](#the-lines-the-owner-sees): a `To record it:`
line, then a `Not interested:` or a `Not a map topic:` line, then the
explanation, the skipped line, the `Map` lines of steps 6 and 7, a `Shown`
line, one question that talks a level through, and the options last. Each
line the table names starts with its word and is one line.

**The skipped line** closes the explanation of every reply that explains a
topic by the map, in the first round or a later one, so that the owner can
object. It names every skipped topic with the level the map has for it, or
as `not assessed`, and says `nothing` when nothing was skipped:

```
Skipped: transactions (practical), connection pools (not assessed).
Skipped: nothing; pitched CRDTs as new to you, say so if not.
Skipped: transactions (practical); pitched advisory locks at practical, as you said.
```

The second form is for a touched topic with no entry and nothing in the
prompt's words; the third for a level the owner only claimed (step 1). The
line is always written, also when nothing was skipped: an exchange without
it is one that did not read the map.

**The ways deeper** close the reply as a numbered list, one line each, a
few, the most useful first, and also as a list of one when there is only one
way, so that the owner's answer is always a number:

```
1. How the lock table works inside, and what a dropped connection does to a session-level lock (advisory locks, toward advanced)
2. What else a commit releases, and in which order (transactions, toward advanced)
```

A line names the way, what it adds, and the topic and level it leads to. A
way is a gap of the explained topic, a child the map shows below the pitched
level or not assessed, the topic's own next level, a related topic the
explanation leaned on, or a needed topic explained in a few words. No way
leads into a not-interested topic. An option is a way the agent would
recommend, written so that the owner can choose without reading more; not a
quiz, and not a menu of everything. The reply that offers the options
explains none of them, and no way is taken before the owner answers.

**The way the owner picks**, by number or in words, is the next round: it is
explained at the level the option named, with its own `attempt` line, and the
map still rises only on evidence (step 6). A way that is a gap of the topic
is explained under the topic's own path, with the gap named in `shown`; it
becomes a child topic of its own, and leaves the parent's `gaps`, only when
step 6 has a level for it on its own.

### Step 5: the attempt line

Every reply that shows the owner something writes one `attempt` line: the
explanation of the first round, each way deeper the owner picked, each answer
to a question that shows something not shown before in the exchange, and
each skipped topic explained on the owner's objection. A reply that shows
nothing writes none: one that only offers the options, only asks back, only
repeats what was shown in other words, only gives the `Not interested:` or
`Not a map topic:` line, or only answers a showup.

- `topics`: the paths of the topics the reply explained, those its
  explanation was pitched for; never the skipped ones, of which nothing was
  shown. A gap explained is logged under its topic's path, and named in
  `shown`.
- `shown`: what was shown, in one or two sentences, in general terms: "the
  two scopes of an advisory lock, and that the transaction scope ends at
  commit", never what the owner's own program does with a lock. Never the
  owner's reactions: the log records what the owner was shown, the map what
  they have shown they understand.
- `before`: each of those topics with the level it showed at the start of
  the round; a topic without entries is left out, so `before` may be `{}`.
- `session`: as [The session](#the-session) says.

### Step 6: the assessment

At the end of every round, the agent judges again every topic the exchange
has touched so far, from everything the owner has said in the exchange so
far, not from the last message alone: three messages may together describe
the routine task that none of them describes alone. In the first round the
words are the prompt's own. This is the periodic check whether a level has
risen; it is not the command `check`, which knows nothing of levels.

**By the tests, and by no other rule**, the tests of the five levels
([CLB-0](../../colab/specs/00-the-nex-knowledge-map.md#the-five-levels)).
Never from what the agent showed, from the number of rounds, or from how long
the owner has used something. Words of the owner's meet a test when they
could only come from someone who can do what the test names: they reason
*with* the thing, not merely *about* it.

| Level | Its test: the owner can… | Words that meet it | Words that do not |
|---|---|---|---|
| *superficial* | explain the idea in a few sentences | use the idea correctly: "so the lock went because the transaction ended, not because of the commit statement itself"; the prompt's own framing, when it shows what the topic is for | asking what it is for |
| *practical* | carry out a routine task with it alone | describe a routine task carried out alone, name a common case or a common mistake from experience, or correct the agent on routine use | asking how to do it; choosing an option |
| *advanced* | explain why it behaves as it does, and say when not to use it | reason about why it behaves as it does, about a limit, or about when not to use it: "a session-level lock held by a pooled connection would travel to the connection's next user, is that why the transaction scope exists?" | asking why it behaves as it does; asking for the inside |
| *design* | lay out how one would build it, with its trade-offs | lay out how one would build it, or weigh a design choice of it against another | asking how it is built |

*Ignorant* is the owner who cannot say what the topic is for.

- A question that only asks for more is no proof; it is the next attempt. The
  choice of a way deeper is no proof. Repeating the agent's words is no
  proof, and neither are words that only restate or recombine what this
  exchange has just shown: words meet a test when they add a case, a
  consequence or a comparison the agent did not make.
- Words about a topic the exchange has not touched are not assessed.
- The level written is the highest whose test is met, whatever the level
  before and however many rounds it took: a first prompt that reasons about
  the inside of a topic the map has at *ignorant* meets *advanced*.
- Each topic rests on its own words: nothing is written to a child from its
  parent, or to a parent from its children.

**What the agent reads for it**, for each topic: its entries, and the log
lines that name its path or one of its `former` paths since its newest entry,
of this exchange and of earlier ones. *Since its newest entry* means the lines
whose `at` is later than the `assessment` or `statement` line that wrote that
entry; for an entry the owner made by hand, which has no log line, the lines
from the day after its date; for a topic with no entry, every line.

**The result:**

- **The level holds:** nothing is written. The log has no line for "checked
  and held".
- **The level rose:** a new entry goes at the top of the topic's `entries`,
  and `level` follows it:

  ```
    - level: advanced
      source: agent
      date: 2026-10-21
      evidence: "exchange on advisory locks, claude-code session <session>; test of advanced met: reasoned that a session-level lock held by a pooled connection would pass to the connection's next user"
  ```

  The evidence has the form `exchange on <topic>, <tool> session <id>; test
  of <level> met: <what the owner said or asked, in general terms>`. One
  `assessment` line goes to the log, with `before`, `level` and `evidence`
  `test of <level> met: <…>`. One `Map:` line goes into the reply, so that
  the owner sees every change to their map when it is made:
  `Map: advisory locks superficial → advanced: you reasoned about lock scope and pooled connections.`
  A topic with no entry that the exchange shows a level for gets its first
  entry the same way; its `assessment` line leaves it out of `before`, and
  the line is `Map: <topic> → <level>: <the test met>.`
- **The level fell**, as below: written, logged and said the same way.

**Lowering a level.** The owner's words about their knowledge are a starting
value, never believed blindly, and that holds for the owner's own entries
too.

- *A gap starts it:* the owner's words in the exchange say they cannot do
  what the shown level's test names. They say they do not know the topic, or
  use it in a way the test rules out, such as calling a commit the end of the
  connection while transactions stand at *practical*. Whoever wrote the
  level, the owner or an agent, makes no difference.
- *Not a gap:* a forgotten detail, a wrong guess, a question about an
  unusual case, a request to explain a skipped topic, or asking for the next
  level. Everyone at *practical* looks things up.
- *Re-evaluated by the tests:* judge the topic again from everything the
  owner said in the exchange, and do not lower it on one remark when the rest
  of the exchange shows the level met. The agent may first ask one question
  that tests the shown level, and judge after the answer.
- *Written as a rise is:* the new level is the highest whose test the
  exchange still shows met, or one level down when the words show only that
  the shown level's test is not met; a new entry of the agent's at the top,
  an `assessment` line and a `Map:` line:
  `Map: transactions practical → superficial: you said you have not used commit yourself.`
  When the level it replaces is the owner's own entry, the line says so:
  `Map: transactions practical → superficial, re-evaluating your own entry: you said you have not used commit yourself; showup restates it.`
  The owner's entry is never changed or deleted; it stays in the history, and
  the owner restates their level with showup if they disagree.

**Talking a level through.** When the owner's words sit between two levels'
tests, the agent may close its reply, before the options, with one question
that invites the owner to reason with the topic, such as "would a
session-level lock survive a pooled connection?", never a quiz with one
right answer. The owner's answer is evidence like any other; a question left
unanswered changes nothing.

**A topic shown without a rise.** When the round's `attempt` line makes a
topic shown in a third exchange, or a later one, since its newest entry, and
its level has not risen, the reply adds the `Shown` line and still explains
what the round asked:
`Shown in 3 exchanges since superficial: advisory locks; say where you stand (/colab showup), or ask for it another way.`
Exchanges are counted by the distinct `session` of the `attempt` lines that
name the topic since its newest entry, this round's included; the ways deeper
picked in one exchange count once. The owner may also ask at any time,
"remind me where I stand": the reply gives the line for the topics the owner
names, or for the exchange's topics when they name none, also below three.

## showup

`/colab showup "<words>"` is the owner's own statement of their level or
experience in a topic, at any time, also in the middle of an exchange or of
`(use colab)` work ([CLB-2](../../colab/specs/02-showup.md)). This section
will hold its steps in execution order, as CLB-2's "A showup from start to
end" gives them, from the words to the reply; SYL-280 of the
[Nex Colab Saga](../../sagas/nex-colab/saga.md) writes it. Until then the
agent answers a showup with the one line
`showup is not built yet; nothing recorded.`, writes nothing, and, in the
middle of an exchange or of `(use colab)` work, goes on with it as
[An exchange, round by round](#an-exchange-round-by-round) says of a showup
in the middle.

## The lines the owner sees

A reply holds them in the order of this table, each in its form, each one
line starting with the word given. `<topic>` is the topic's title, `<level>`
one of the five levels.

| Line | Form | When |
|---|---|---|
| To record it | `To record it: /colab showup "<the words>"` | first in the reply, when the owner asks in plain words to record a level; nothing is written for it |
| Not interested | `Not interested: <topic> is marked; it is answered without the map and nothing is recorded for it; showup removes the mark.` | at the start of the reply, for a touched topic that is marked |
| Not a map topic | `Not a map topic: <what the prompt is about>; answered without the map, nothing recorded.` | at the start of the reply, for a prompt with no general topic |
| The explanation | free text, pitched as step 3 says | |
| The skipped line | `Skipped: <topic> (<level>), <topic> (not assessed).` or `Skipped: nothing.`; for a touched topic with no entry and nothing in the prompt's words the period gives way to `; pitched <topic> as new to you, say so if not.`; for a level the owner only claimed, to `; pitched <topic> at <level>, as you said.` | after the explanation of every reply that explains a topic by the map |
| Read only | `Map read only: <why>; nothing recorded. Say "update my map" to record.` | first among the `Map` lines of `(use colab)` work that only reads, once per session |
| A change of level | `Map: <topic> <before> → <after>: <the test met, in a few words>.`; for a first entry `Map: <topic> → <level>: <the test met>.` | in the round that wrote the entry |
| A level below the owner's own entry | `Map: <topic> <before> → <after>, re-evaluating your own entry: <the gap, in a few words>; showup restates it.` | in the round that wrote the entry |
| A check error elsewhere | `Map check: <file>: <message>; left as it is.` | after `check`, once per exchange for one file |
| Not pushed | `Map not pushed: <why>; the next push carries it.` | in the round whose push failed |
| Not written | `Map not written: <why>; nothing recorded.` | once per exchange, when the corpus cannot be written |
| Shown without a rise | `Shown in <n> exchanges since <level>: <topic>; say where you stand (/colab showup), or ask for it another way.`; for a topic with no entry `Shown in <n> exchanges, never assessed: <topic>; say where you stand (/colab showup), or ask for it another way.` | in the round that makes it the third exchange or a later one, or when the owner asks to be reminded |
| A question that talks a level through | one question that invites the owner to reason with the topic | before the options, when the owner's words sit between two levels' tests |
| The options | `<n>. <the way> (<topic>, toward <level>)` | last, one per way deeper |
