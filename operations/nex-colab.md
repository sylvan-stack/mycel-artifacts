# Guide: Nex Colab

Use this guide when the owner asks to learn something with `/colab "prompt"`,
states their own level with `/colab showup "<words>"`, asks that their
knowledge be taken into account in other work with `(use colab)`, or starts
learn mode with `/learn`, a whole session of learning and nothing else. The agent answers at the depth the owner's
[Nex Knowledge Map](../../arbol/GLOSSARY.md#nex-knowledge-map) says is
missing, closes each reply that teaches with a short quiz, logs every time it
shows the owner something, judges from the owner's own words and quiz answers
whether a level has risen or fallen, lists what it changed in the map, and
writes the map and the log, then commits and pushes them, after each reply of
the owner's.
[Nex Colab](../../arbol/GLOSSARY.md#nex-colab) is that exchange: the owner
is its [H-Nex](../../arbol/GLOSSARY.md#h-nex), the agent an
[A-Nex](../../arbol/GLOSSARY.md#a-nex).

This guide is authoritative for the steps an agent takes and the lines it
says, in Claude Code, in Codex and in an Arbol chat; an agent needs this
guide alone. What the steps must achieve, and why, is in the specifications
of the private corpus `~/Artifacts/colab/`:
[CLB-0](../../colab/specs/00-the-nex-knowledge-map.md), the map and the log;
[CLB-1](../../colab/specs/01-nex-colab.md), the exchange and `(use colab)`;
[CLB-2](../../colab/specs/02-showup.md), showup;
[CLB-3](../../colab/specs/03-learn.md), learn mode. Read them for a reason, not
for a step. The guide reads and writes the map as data, with the check that
lives in that corpus.

**Contents:** when to use · the corpus and its files · an exchange, round by
round, from the prompt to writing the map and the log · (use colab) · showup,
from the words to the reply · learn mode,
from the goal to leaving · the lines the owner sees · what the agent never
does · the samples.

## When to use

| The owner writes | It starts | Section |
|---|---|---|
| `/colab "<prompt>"`; in Codex `$colab "<prompt>"` | an exchange | [An exchange, round by round](#an-exchange-round-by-round) |
| `/colab showup "<words>"`; in Codex `$colab showup "<words>"` | a showup: the owner states their own level | [showup](#showup) |
| `(use colab)` anywhere in a message, or `/use-colab <message>`; in Codex `$use-colab <message>` | the map used in that work | [(use colab)](#use-colab-the-map-in-other-work) |
| `/learn "<goal>"` or `/learn`; in Codex `$learn "<goal>"` or `$learn` | learn mode: a whole session in which the agent only teaches | [Learn mode](#learn-mode) |

Nothing else starts any of them. A question that only looks like a learning
question, "what is a CRDT?" or "help me get ready for an interview", gets an
ordinary answer, which says nothing of the map, the log or these skills and
does not offer them; and a message without
the phrase `(use colab)`, outside an exchange and learn mode, neither reads
nor writes the map. The skill `colab` starts on its two forms only, the first
word `showup` choosing the second; the skill `use-colab` starts on the phrase
and on its own name only; the skill `learn` starts on its own name only. Each
hands this guide the whole message.

Every reply speaks to the owner about their topic or their work, in the forms
this guide gives. It never names, quotes or links this guide, a skill or a
file of the corpus to justify what it does or does not do.

## The corpus and its files

The corpus is the folder that the variable `COLAB_CORPUS` names when it is
set, and `~/Artifacts/colab/` when it is not. A sample sets it to point the
agent at a fictional corpus; the owner never does. Find it once per session:

```bash
printf '%s\n' "${COLAB_CORPUS:-$HOME/Artifacts/colab}"
```

Below, `<corpus>` is the folder this prints.

**The corpus is private**, because the map describes the owner. Its levels
are quoted to the owner in the session and nowhere else: nothing of `map/`
or `log/` goes into a reply outside the owner's session, another corpus, a
specification, a Linear page or a sample's fixtures. Every note, evidence and
`shown` speaks of the owner's learning in general terms and never names a
repository, a project or a product, the owner's own included, also when the
prompt was about one ([CLB-0, Privacy](../../colab/specs/00-the-nex-knowledge-map.md#privacy)).

| File | What it is |
|---|---|
| `map/INDEX.md` | Every topic on one line, nested as the tree is: its title linked to its file, its level or `not assessed`, and `also:` with its aliases; then `## Not interested` with the paths of the marked topics. Generated by `index`; never edited by hand |
| `map/<path>/topic.md` | One topic. Its folder's path from `map/` is its identifier, such as `software-development/postgresql/advisory-locks`; the folders inside it are its children |
| `log/<YYYY-MM>.jsonl` | The learning log of one UTC month, one JSON object per line, appended and never changed |

### A topic's file

A key block between two lines of `---`, then the body. Fictional example:

```
---
title: Advisory locks in PostgreSQL
level: superficial
aliases:
  - advisory locks
entries:
  - level: superficial
    source: agent
    date: 2026-10-21
    evidence: "exchange on advisory locks, claude-code session <session>; test of superficial met: took a lock inside a transaction and expected it to stay, which shows what the lock is for"
related:
  - software-development/postgresql/transactions
gaps:
  - lock timeouts
---
# Advisory locks in PostgreSQL

The two scopes, session and transaction, were new; the example of a
pooled connection worked.
```

| Key | When | What |
|---|---|---|
| `title` | always | The full name, in a few words |
| `level` | when there are entries | The newest entry's level; absent without entries |
| `aliases` | optional | Other names a prompt may use |
| `entries` | optional | Newest first; each with `level`, `source` (`owner` or `agent`), `date` (`YYYY-MM-DD`, UTC) and `evidence` |
| `related` | optional | Paths of related topics; each link written in both topics |
| `gaps` | optional | Parts of the topic not learned yet, a few words each |
| `former` | optional | Paths the topic had before the owner moved it |
| `not-interested` | optional | `true`: the owner does not want to learn this topic or anything under it. Set and removed on the owner's word only |

The block is a small subset of YAML, and `check` reports anything else: one
`key: value` per line; a list as `key:` followed by lines `  - item`; an
entry as `  - level: …` followed by `    source: …`, `    date: …` and
`    evidence: …`; a value in double quotes when it holds `:` or `#`, with
`\"` and `\\` as the only escapes; `not-interested: true` never quoted; no
comment, no blank line, no tab, no `[a, b]` list and no value over several
lines. The level is one of *ignorant*, *superficial*, *practical*,
*advanced* and *design*. The body holds the notes for pitching an answer:
what the owner knows the topic through, what confused them, which examples
worked. `index` writes a section `## Children` at the end of the body when
the topic has children; nothing is written below it by hand. The folder's
name is lower-case ASCII letters and digits, words joined by hyphens, and
every folder under `map/` holds a `topic.md`. The full form is
[CLB-0's Interface](../../colab/specs/00-the-nex-knowledge-map.md#interface).

### A log line

One JSON object on one line, with exactly the keys of its kind. Every line
has `at` (UTC, `2026-10-21T09:14:02Z`), `kind`, `session` and `topics` (the
paths it is about). An exchange writes three kinds; the fourth, `statement`,
is showup's.

| Kind | When | Its own keys |
|---|---|---|
| `added` | a topic is added to the map | `reason`: why, one sentence |
| `attempt` | a reply showed the owner something | `shown`: what, one or two sentences; `before`: path → level of each topic shown, a topic without entries left out |
| `assessment` | a level changed | `before`: path → level, a topic without entries left out; `level`: path → the new level; `evidence`: the test met |

Fictional example, one round that added a topic, showed it and raised it:

```
{"at":"2026-10-21T09:14:01Z","kind":"added","session":"claude-code <session>","topics":["software-development/postgresql/advisory-locks"],"reason":"needed for a question on why an advisory lock is gone after commit"}
{"at":"2026-10-21T09:14:02Z","kind":"attempt","session":"claude-code <session>","topics":["software-development/postgresql/advisory-locks"],"shown":"the two scopes of an advisory lock, session and transaction, when each fits, and that a transaction-level lock is released at commit","before":{}}
{"at":"2026-10-21T09:14:03Z","kind":"assessment","session":"claude-code <session>","topics":["software-development/postgresql/advisory-locks"],"before":{},"level":{"software-development/postgresql/advisory-locks":"superficial"},"evidence":"test of superficial met: took a lock inside a transaction and expected it to stay, which shows what the lock is for"}
```

The full form is
[CLB-0's Interface](../../colab/specs/00-the-nex-knowledge-map.md#interface).

### The session

`session`, in every log line, names the tool and the session the agent runs
in. The evidence of an entry names the same two with the word `session`
between them: `claude-code session <session id>`, `codex session <thread id>`.

| The agent runs in | `session` | Where the identifier is |
|---|---|---|
| Claude Code | `claude-code <session id>` | the variable `CLAUDE_CODE_SESSION_ID` |
| Codex | `codex <thread id>` | the variable `CODEX_THREAD_ID` |
| An Arbol chat | the chat's [Entity URI](../../arbol/GLOSSARY.md#entity-uri) | given to the agent with the chat |

### The commands

The check of the map is `~/Artifacts/colab/tools/knowledge_map.py`, Python's
standard library only. It works on the folder it is started in, so it is run
from the corpus, whichever corpus that is:

```bash
cd "<corpus>" && python3 ~/Artifacts/colab/tools/knowledge_map.py index
cd "<corpus>" && python3 ~/Artifacts/colab/tools/knowledge_map.py check
```

- **`index`** regenerates `map/INDEX.md` and every topic's `## Children`
  section, prints `wrote <file>` for each file it changed, and changes nothing
  else. When a topic has an error other than an out-of-date summary, it
  writes nothing, lists the errors and exits 1.
- **`check`** prints one line `<file>: <message>` for each file of `map/` and
  `log/` that is out of form, sorted by file, and exits 1; it prints nothing
  and exits 0 when the corpus is in form. It checks the form of the files and
  knows nothing of levels.

Git: the corpus is committed and pushed only when it is a git repository of
its own, `git -C "<corpus>" rev-parse --show-toplevel` printing `<corpus>`,
with the identity git already has and no agent credit.

## An exchange, round by round

An exchange is made of *rounds*: one message of the owner's and the agent's
reply to it. The first round's message is `/colab "<prompt>"`. A later
message is a round when it stays on the exchange's topics: one number from
the last list of options, the answers to the last quiz, an objection to the
last skipped line, or a question or a statement about a topic the exchange
has touched. A number
that is not on the list gets one question back. Any other message ends the
exchange, without a word said: thanks, other work, another
`/colab "<prompt>"`, which starts a new exchange, or the session closing. An
owner who comes back to a topic the next day starts a new exchange; the log
ties the two by the topic's path.

Two kinds of message neither end the exchange nor are rounds:

- **A showup in the middle**, `/colab showup "<words>"`. Its message, its
  question and every message that answers the question, up to the showup's
  reply, belong to the showup: they show nothing, write no `attempt` line and
  no skipped line, and are no evidence for the exchange's assessment. The
  agent records it as [showup](#showup) says, then goes on with the exchange:
  it reads the files of the topics the showup changed again, pitches what it
  shows next at the new level, and says in one line what it now skips. What
  it shows after the showup, in the same reply or the next, is a round. A
  mark set on the topic being explained ends that explanation. Words that
  name no topic, `/colab showup "advanced in this"`, refer to the topics of
  the exchange's last `attempt` line.
- **A request in plain words to record a level**, "note that I know this
  well". The reply begins with the `To record it:` line, and nothing is
  written for it.

The agent cannot see a session end, so it treats every round as possibly the
last: everything a round changed is in the map, in the log and pushed before
its reply is given.

**The first round** takes seven steps:

1. [The prompt](#step-1-the-prompt): is it a Nex Colab prompt, and what is
   its general topic?
2. [The topics](#step-2-the-topics): the topics the prompt touches and the
   topics the answer needs, found in the map, read, and set aside when the
   owner is not interested in them.
3. [The depth](#step-3-the-depth): topic by topic, what is skipped and what
   is explained, at which level.
4. [The reply](#step-4-the-reply): the explanation, the skipped line, and
   the three closing blocks: the quiz, the list of changes, and the ways
   deeper as numbered options last.
5. [The `attempt` line](#step-5-the-attempt-line) for what the reply shows.
6. [The assessment](#step-6-the-assessment): from the owner's words in the
   exchange so far, whether a level has risen or fallen, over every topic the
   exchange has touched.
7. [Writing the map and the log](#step-7-writing-the-map-and-the-log):
   the files, `index`, `check`, the commit and the push.

**Every later round** takes steps 3 to 7 for what its message asks. A number
picks an option: the round explains that way, pitched at the level the option
named. A question is answered at the owner's depth, and is the evidence step
6 reads. An objection to the skipped line is answered by explaining what was
skipped, or by moving the pitch up, as step 3 says. The answers to the last
quiz, `1b 2d 3a`, alone or with a number, are marked first in the reply, and
step 6 reads them as evidence. An answer that says the owner is done, or that
is other work, ends the exchange.

Nothing is written before step 7, and every `before` is the level a topic
showed at the start of the round. Steps 4 to 6 prepare the reply; it is
given once step 7 is done, so that its lines say what was written.

### Step 1: the prompt

The prompt is what the owner wants to learn, in their own words.

- **A question in general**, "what is a CRDT?", "advisory locks": the topics
  are in the words.
- **A question about something in the current session**, "why did you use a
  fixture in the test you just wrote?": name the general topic behind the
  thing, test fixtures, and explain that topic at the owner's depth with the
  thing in the session as its example. The map and the log record the
  general topic only, in general terms: "asked why a test needs a fixture",
  never what the test or its repository is.
- **No general topic behind it**, "what does this project's `retry` setting
  do?": the test is whether someone could learn it from public sources,
  without access to a particular repository, project or product. When not,
  it is no Nex Colab prompt: answer it as without Nex Colab, write nothing
  to the map or the log, and begin the reply with the `Not a map topic:`
  line. A prompt that mixes the two, "why does this project's retry loop use
  exponential backoff?", is a Nex Colab prompt about its general topic,
  exponential backoff.

The prompt need not name a level: the map supplies it. Words that *use* a
topic, "I took the lock inside the transaction and expected it to stay", are
evidence that step 6 reads. Words that only *claim* a level, "I use
transactions every day" or "I am new to this", meet no test by themselves:
pitch the round at the level they name, say so in the skipped line, and
write no entry for the claim alone. A claim not to know a topic is the one
exception: it is evidence for lowering the level shown (step 6). A claim
becomes the owner's own entry only through a showup.

### Step 2: the topics

Run `index` before reading anything of the corpus, since `map/INDEX.md` may
be out of date until it has run; then read `map/INDEX.md` once. Match the subjects of the prompt
against the titles, the aliases and the paths, and decide two sets before
writing a word of the explanation:

- **The topics the prompt touches**: what the owner asks about, the subjects
  in its words or the general topic behind the thing in the session.
- **The topics the answer needs**: what an explanation of the touched
  topics, at the depth it will be pitched, rests on and cannot do without. In
  "why is my advisory lock gone after commit?", transactions, because a lock
  gone at commit cannot be explained to someone who does not know what a
  commit ends. A topic the explanation could mention but does not need is in
  neither set; it may be a way deeper.

Read the `topic.md` of every topic in both sets, and no other: its level,
its entries, its gaps and its notes, which say what confused the owner
before and which examples worked. Read the log lines that name its path, or
one of its `former` paths, since its newest entry (step 6 says which those
are): what was shown before is not shown again the same way.

- **A topic found under another parent, or under one of its aliases**, is
  used; it is never created a second time.
- **A topic with no entry** is *not assessed*: unknown, never *ignorant*.
- **A topic the map lacks** is noted. Step 7 adds it, but only when the round
  explains or assesses it, not when it is only skipped. It goes under the
  parent you judge right from the field the prompt belongs to and the topics
  already there, or as a new field at the top of `map/`, with every folder on
  the way. Prefer a shallow tree: `software-development/postgresql/advisory-locks`,
  not a chain of folders made for one topic. The map started empty, so an
  agent that finds nothing for a prompt is in the normal case.
- **A topic the owner is not interested in**, marked `not-interested: true`
  in its own file or in an ancestor's, is outside the map. `map/INDEX.md`
  lists marked topics by path only, under `## Not interested`: before
  matching, read the `topic.md` of each listed path in the prompt's field,
  for its title and aliases. When the prompt touches one, begin the reply
  with the `Not interested:` line and answer it plainly, at whatever depth
  the question needs, as any agent would. For that topic and everything under
  it, write no entry, gap, alias or log line, create no topic, pitch no
  explanation, offer no way deeper and follow no related link. A needed topic
  that is marked is used plainly and recorded nowhere. The other topics of
  the prompt are handled as usual. The mark is set and removed on the
  owner's word only, through showup or by hand, never on the agent's
  judgement.

### Step 3: the depth

The depth is decided topic by topic, for every topic the prompt touches and
every topic the answer needs, by the level the map shows. The rule is one
level up: the explanation gives what the test of the next level names, and
no more.

| The map shows | The explanation gives | So that the owner can, afterwards… |
|---|---|---|
| *ignorant*, or no entry and nothing in the prompt's words | what the topic is for and roughly how it works, in a few sentences, with one example | explain the idea in a few sentences |
| *superficial* | how to carry out the routine task: the steps, the common cases and the common mistakes, and where its documentation is | carry out a routine task with it alone |
| *practical* | how it works inside, its limits and its trade-offs, the alternatives and when not to use it | explain why it behaves as it does, and say when not to use it |
| *advanced* | how one would build it, with its trade-offs | lay out how one would build it |
| *design* | nothing more of the topic in general; a precise question is still answered, and the way deeper is a child, a gap or a related topic, which the reply says | — |

- **The pitch** rests on the level the topic shows, or on the higher level
  that the prompt's own words meet by the tests of step 6: a prompt that
  reasons about the inside of a topic the map has at *ignorant* is answered
  at the depth its words show, and step 6 brings the map up in the same
  round.
- **A precise question**, "how does the lock table work inside?", is
  answered at the depth it asks, whatever the level; the table pitches what
  the answer needs around it.
- **A touched topic with no entry**, and nothing in the prompt's words: pitch
  it for someone who does not know what it is for, write no entry, and say
  so in the skipped line.
- **A needed topic** is *skipped*, used without being explained, when the map
  has it at the level the explanation needs the owner to have in it, or
  higher. One the map has below that level is explained too, in the fewest
  words that let the explanation stand, pitched by the table, and offered as
  a way deeper of its own. One with no entry, or not in the map, is skipped
  and named in the skipped line as `not assessed`, so that the owner objects
  when they need it. Skipping writes nothing.
- **The notes** steer the wording: the example that worked before is reused,
  the one that confused is not, and one the log shows was shown before is not
  shown again.
- **An objection** to the skipped line is answered in the next round.
  "Explain transactions too": explain what was skipped. "I know advisory
  locks, go on" or "I am not new to CRDTs": a claim, so go on at the level
  the owner names; writing it into the map is the owner's showup.

### Step 4: the reply

No sentence of the reply, at its start or anywhere else, says what the
round wrote, logged or pushed: the list of changes says what changed. The
reply holds its lines in the order of
[The lines the owner sees](#the-lines-the-owner-sees): the marking, when the
owner's message answered the last quiz; a `To record it:` line; a
`Not interested:` or a `Not a map topic:` line; the explanation; the skipped
line; a `Map check:`, `Map not pushed:` or `Map not written:` line of step 7;
a `Shown` line; one question that talks a level through; and then the three
blocks that close it, in this order: the quiz, the list of changes of step 6,
and the options last. Each line the table names starts with its word and is
one line. Each of the three closing blocks is a Markdown heading of the third
level with its title, a blank line, and the block's lines, written the same
way in every reply so that the owner learns where to look:

```
### Quiz

Answer as 1b 2d 3a, or skip it.

1. <the question>
   - a) <option>
   - b) <option>
   - c) <option>
   - d) <option>

### Learnings

- <topic>: <before> → <after>: <the reason, in a few words>.

### Do you want to proceed with...

1. <the way> (<topic>, toward <level>)
```

The titles are word for word, three dots included, and nothing else stands
under a title but its block's lines. The `Learnings` block stands only in a
round that changed the map; the other two close every reply that shows
something.

**The skipped line** closes the explanation of every reply that explains a
topic by the map, in the first round or a later one, so that the owner can
object. It names every skipped topic with the level the map has for it, or
as `not assessed`, and says `nothing` when nothing was skipped:

```
Skipped: transactions (practical), connection pools (not assessed).
Skipped: nothing; pitched CRDTs as new to you, say so if not.
Skipped: transactions (practical); pitched advisory locks at practical, as you said.
```

The second form is for a touched topic with no entry and nothing in the
prompt's words; the third for a level the owner only claimed (step 1). The
line is always written, also when nothing was skipped: an exchange without
it is one that did not read the map.

**The quiz** closes every reply that shows the owner something, the reply
that writes an `attempt` line (step 5), after the skipped line, a `Shown`
line and a question that talks a level through, and before the list of
changes and the options. It assesses what the owner understood of what this
reply showed:

- **2 to 10 questions**, about one for each idea the reply showed, and at
  least two on each topic it explained, as far as ten allow: two or three
  after a short explanation, more after a long one over several topics.
- **A case the reply did not show.** Each question asks the owner to apply
  what the reply showed to a new case, a consequence or a comparison the
  reply did not make; never to repeat one of its sentences. Write it for the
  test of the level the reply pitched its topic toward (step 3): after an
  explanation of the routine task, a question on what to do in a case the
  reply did not give, the test of *practical*.
- **Four options, one right.** Options of a few words, plausible to someone
  who has not understood, the common mistakes among them; the right one's
  letter changes from question to question. A topic at *design* gets
  questions too, though they raise nothing.

The quiz is its title `### Quiz`, the line `Answer as 1b 2d 3a, or skip it.`,
word for word, then each question numbered from 1, with its four options
under it, one per line:

```
### Quiz

Answer as 1b 2d 3a, or skip it.

1. A report job takes a lock, runs three queries in three transactions and must hold the lock throughout. Which scope does it need?
   - a) transaction-level
   - b) session-level
   - c) either, they behave alike
   - d) none, a commit keeps every lock
2. A pooled connection returns to the pool while it still holds a session-level lock. What happens to the lock?
   - a) it is released on return
   - b) it is released at the next commit
   - c) it stays with the connection
   - d) the pool raises an error
```

The owner answers in their next message, `1b 2c`, alone or with a number
that picks a way deeper (`1b 2c, then 1`), or not at all: an unanswered quiz
changes nothing. Only the last quiz is answered; an earlier one lapses when a
later reply gives a new one. No other reply holds a quiz: not one that shows
nothing, such as a `Not interested:` or `Not a map topic:` answer or a reply
that only marks a quiz, not `(use colab)` work and not a showup's reply.

**The marking** opens the reply to a message that answers the last quiz,
before every other line: its first line, then one line per question of that
quiz, in its order:

```
Quiz answers: 1 of 2 right.
- 1b: right.
- 2a: wrong; c) it stays with the connection: a session-level lock lasts as long as the session, and the pool keeps the session open.
```

A question the owner left out is `- <n>: not answered.` The marking shows
nothing new, so a reply that only marks writes no `attempt` line and gives no
quiz; it ends, as the reply the quiz closed did, with the ways deeper, which
may offer the part a wrong answer missed. Step 6 reads the answers.

**The ways deeper** close the reply, after the quiz and the list of changes,
under the title `### Do you want to proceed with...`, as a numbered list, one
line each, a few, the most useful first, and also as a list of one when there
is only one way, so that the owner's answer is always a number:

```
### Do you want to proceed with...

1. How the lock table works inside, and what a dropped connection does to a session-level lock (advisory locks, toward advanced)
2. What else a commit releases, and in which order (transactions, toward advanced)
```

A line names the way, what it adds, and the topic and level it leads to, and
ends with the closing parenthesis, with no period after it. A
way is a gap of the explained topic, a child the map shows below the pitched
level or not assessed, the topic's own next level, a related topic the
explanation leaned on, or a needed topic explained in a few words. No way
leads into a not-interested topic. An option is a way the agent would
recommend, written so that the owner can choose without reading more; not a
quiz, and not a menu of everything. The reply that offers the options
explains none of them, and no way is taken before the owner answers.

**The way the owner picks**, by number or in words, is the next round: it is
explained at the level the option named, with its own `attempt` line, and the
map still rises only on evidence (step 6). A way that is a gap of the topic
is explained under the topic's own path, with the gap named in `shown`; it
becomes a child topic of its own, and leaves the parent's `gaps`, only when
step 6 has a level for it on its own.

### Step 5: the attempt line

Every reply that shows the owner something writes one `attempt` line: the
explanation of the first round, each way deeper the owner picked, each answer
to a question that shows something not shown before in the exchange, and
each skipped topic explained on the owner's objection. A reply that shows
nothing writes none: one that only offers the options, only asks back, only
repeats what was shown in other words, only marks a quiz, only gives the
`Not interested:` or `Not a map topic:` line, or only answers a showup.

- `topics`: the paths of the topics the reply explained, those its
  explanation was pitched for; never the skipped ones, of which nothing was
  shown. A gap explained is logged under its topic's path, and named in
  `shown`.
- `shown`: what was shown, in one or two sentences, in general terms: "the
  two scopes of an advisory lock, and that the transaction scope ends at
  commit", never what the owner's own program does with a lock. Never the
  owner's reactions: the log records what the owner was shown, the map what
  they have shown they understand.
- `before`: each of those topics with the level it showed at the start of
  the round; a topic without entries is left out, so `before` may be `{}`.
- `session`: as [The session](#the-session) says.

### Step 6: the assessment

At the end of every round, the agent judges again every topic the exchange
has touched so far, from everything the owner has said in the exchange so
far, not from the last message alone: three messages may together describe
the routine task that none of them describes alone. In the first round the
words are the prompt's own. This is the periodic check whether a level has
risen; it is not the command `check`, which knows nothing of levels.

**By the tests, and by no other rule**, the tests of the five levels
([CLB-0](../../colab/specs/00-the-nex-knowledge-map.md#the-five-levels)).
Never from what the agent showed, from the number of rounds, or from how long
the owner has used something. Words of the owner's meet a test when they
could only come from someone who can do what the test names: they reason
*with* the thing, not merely *about* it.

| Level | Its test: the owner can… | Words that meet it | Words that do not |
|---|---|---|---|
| *superficial* | explain the idea in a few sentences | use the idea correctly: "so the lock went because the transaction ended, not because of the commit statement itself"; the prompt's own framing, when it shows what the topic is for | asking what it is for |
| *practical* | carry out a routine task with it alone | describe a routine task carried out alone, name a common case or a common mistake from experience, or correct the agent on routine use | asking how to do it; choosing an option |
| *advanced* | explain why it behaves as it does, and say when not to use it | reason about why it behaves as it does, about a limit, or about when not to use it: "a session-level lock held by a pooled connection would travel to the connection's next user, is that why the transaction scope exists?" | asking why it behaves as it does; asking for the inside |
| *design* | lay out how one would build it, with its trade-offs | lay out how one would build it, or weigh a design choice of it against another | asking how it is built |

*Ignorant* is the owner who cannot say what the topic is for.

- A question that only asks for more is no proof; it is the next attempt. The
  choice of a way deeper is no proof. Repeating the agent's words is no
  proof, and neither are words that only restate or recombine what this
  exchange has just shown: words meet a test when they add a case, a
  consequence or a comparison the agent did not make.
- **The quiz's answers** are the one place where choosing among options
  the agent wrote is proof: when the owner answers right every question of
  the last quiz on a topic, and they are at least two, the test of the level
  those questions were written for is met. Fewer right answers meet no test,
  since one right pick in four is a guess; a question not answered counts as
  not right. A wrong answer is a wrong guess: it lowers nothing. The
  evidence names the quiz: `test of practical met: answered right the 3 quiz
  questions on <what they asked, in general terms>`.
- Words about a topic the exchange has not touched are not assessed.
- The level written is the highest whose test is met, whatever the level
  before and however many rounds it took: a first prompt that reasons about
  the inside of a topic the map has at *ignorant* meets *advanced*.
- Each topic rests on its own words: nothing is written to a child from its
  parent, or to a parent from its children.

**What the agent reads for it**, for each topic: its entries, and the log
lines that name its path or one of its `former` paths since its newest entry,
of this exchange and of earlier ones. *Since its newest entry* means the lines
whose `at` is later than the `assessment` or `statement` line that wrote that
entry; for an entry the owner made by hand, which has no log line, the lines
from the day after its date; for a topic with no entry, every line.

**The result:**

- **The level holds:** nothing is written. The log has no line for "checked
  and held".
- **The level rose:** a new entry goes at the top of the topic's `entries`,
  and `level` follows it:

  ```
    - level: advanced
      source: agent
      date: 2026-10-21
      evidence: "exchange on advisory locks, claude-code session <session>; test of advanced met: reasoned that a session-level lock held by a pooled connection would pass to the connection's next user"
  ```

  The evidence has the form `exchange on <topic>, <tool> session <id>; test
  of <level> met: <what the owner said or asked, in general terms>`, with the
  word `session` between the tool and the identifier, `claude-code session
  <id>`, though the log line's `session` has none. One
  `assessment` line goes to the log, with `before`, `level` and `evidence`
  `test of <level> met: <…>`. One line goes into the reply's list of changes,
  so that the owner sees every change to their map when it is made:
  `- Advisory locks: superficial → advanced: you reasoned about lock scope and pooled connections.`
  A topic with no entry that the exchange shows a level for gets its first
  entry the same way; its `assessment` line leaves it out of `before`, and
  its line names `not assessed` as the old level:
  `- Advisory locks: not assessed → superficial: <the test met>.`
- **The level fell**, as below: written, logged and said the same way.

**The list of changes** says, in the reply, what the round changed in the
map: after the quiz and before the options, the title `### Learnings` and one
line for each topic whose level the round changed and for each topic it
added to the map, the folders on the way included:

```
### Learnings

- Advisory locks: superficial → practical: answered right the 3 quiz questions on choosing a lock's scope.
- Vector clocks: new topic → not assessed: added for your question on ordering edits.
```

The old level is `not assessed` for a first entry and `new topic` for a
topic the round added; a topic added without an entry ends at
`not assessed`, with why it was added. Gaps, aliases, related links and
notes change no level and no topic, and are not listed. A round that changed
nothing has no list. In `(use colab)` work each change is its one-line
`Map:` line instead, and there is no list.

**Lowering a level.** The owner's words about their knowledge are a starting
value, never believed blindly, and that holds for the owner's own entries
too.

- *A gap starts it:* the owner's words in the exchange say they cannot do
  what the shown level's test names. They say they do not know the topic, or
  use it in a way the test rules out, such as calling a commit the end of the
  connection while transactions stand at *practical*. Whoever wrote the
  level, the owner or an agent, makes no difference.
- *Not a gap:* a forgotten detail, a wrong guess, a question about an
  unusual case, a request to explain a skipped topic, or asking for the next
  level. Everyone at *practical* looks things up.
- *Re-evaluated by the tests:* judge the topic again from everything the
  owner said in the exchange, and do not lower it on one remark when the rest
  of the exchange shows the level met. The agent may first ask one question
  that tests the shown level, and judge after the answer.
- *Written as a rise is:* the new level is the highest whose test the
  exchange still shows met, or one level down when the words show only that
  the shown level's test is not met; a new entry of the agent's at the top,
  an `assessment` line and a line in the list of changes:
  `- Transactions: practical → superficial: you said you have not used commit yourself.`
  When the level it replaces is the owner's own entry, the line says so:
  `- Transactions: practical → superficial, re-evaluating your own entry: you said you have not used commit yourself; showup restates it.`
  The entry's evidence keeps the form of a rise, naming first the test of the
  new level that the exchange still shows met, then the gap:
  `exchange on transactions, <tool> session <id>; test of superficial met: <what still meets it>; test of practical not met: <the gap>`,
  and the `assessment` line's `evidence` is its part from `test of`. When the
  level goes one down because the words show only that the shown level's
  test is not met, the gap alone: `…; test of practical not met: <the gap>`;
  so too for *ignorant*, which has no test: `…; test of superficial not met: <the gap>`.
  The owner's entry is never changed or deleted; it stays in the history, and
  the owner restates their level with showup if they disagree.

**Talking a level through.** When the owner's words sit between two levels'
tests, the agent may close its reply, before the quiz, with one open question
that invites the owner to reason with the topic in their own words, such as
"would a session-level lock survive a pooled connection?"; it offers no
options, which are the quiz's. The owner's answer is evidence like any other;
a question left unanswered changes nothing.

**A topic shown without a rise.** When the round's `attempt` line makes a
topic shown in a third exchange, or a later one, since its newest entry, and
its level has not risen, the reply adds the `Shown` line and still explains
what the round asked:
`Shown in 3 exchanges since superficial: advisory locks; say where you stand (/colab showup), or ask for it another way.`
Exchanges are counted by the distinct `session` of the `attempt` lines that
name the topic since its newest entry, this round's included; the ways deeper
picked in one exchange count once. Below three, the reply has no `Shown` line,
unless the owner asks. The owner may also ask at any time,
"remind me where I stand": the reply gives the line for the topics the owner
names, or for the exchange's topics when they name none, also below three.

### Step 7: writing the map and the log

At the end of every round that changed the map or the log, in this order,
so that two sessions writing the map on the same day lose nothing of each
other's:

1. **The topics.** For each topic the round adds or changes, read its file
   immediately before writing it back whole, once in the round. A new entry
   goes at the top of `entries`, and `level` follows it. A note goes into the
   body, above `## Children`. A gap, an alias or a related link goes into its
   key, a related link into both topics. A new topic gets its folder and its
   `topic.md`, with the entry the round showed or with none, and every folder
   on the way that did not exist gets a `topic.md` with its `title` only. The
   agent that creates a child for a gap removes the gap from the parent.
2. **The log.** Append the round's lines to `log/<YYYY-MM>.jsonl`, the file
   of the UTC month of each line's `at`, each line in one write and never
   by rewriting the file: an `added` line before the `attempt` line, the
   `attempt` line before the `assessment` line. The time is
   `date -u +%Y-%m-%dT%H:%M:%SZ`. For example:

   ```bash
   cd "<corpus>" && cat >> log/2026-10.jsonl <<'LINE'
   {"at":"2026-10-21T09:14:02Z","kind":"attempt","session":"claude-code <session>","topics":["software-development/postgresql/advisory-locks"],"shown":"…","before":{}}
   LINE
   ```

3. **`index`, then `check`.** An error that `check` reports in a file this
   round wrote is fixed before the round ends. Undoing this round's own
   uncommitted writes, such as a new alias that coincides with another
   topic's, is a fix and not a deletion. An error in any other file is not
   this exchange's to fix: the reply says so once per exchange,
   `Map check: <file>: <message>; left as it is.`, and the work goes on.
   When that error makes `index` refuse, the round's summaries stay out of
   date until it is fixed, and the round's own files are still committed.
4. **The commit**, made only when `git -C "<corpus>" rev-parse --show-toplevel`
   prints `<corpus>`. Add by name the files this round wrote and the
   summaries `index` printed as written, and nothing else, so that another
   session's half-written round or the owner's unfinished edit is not swept
   in. Before committing, `git -C "<corpus>" status --short -- map log` lists
   every changed file: each one this round wrote or `index` printed goes into
   the commit, the parent whose `## Children` section `index` rewrote
   included. Commit with the identity git already has and no agent credit, with
   the subject `Nex Colab: <the titles of the topics written>`: the topics
   the round wrote, or, when it wrote only log lines, the topics they name.
   A file left out by mistake goes into a further commit with the same
   subject; a commit is never amended and a push is never forced, because
   another session may already have pulled it.
5. **The push.** `git push`. When it is refused because another session
   pushed first, `git pull --no-rebase --no-edit` and push again. A
   conflict in a log file keeps both sides' lines; a conflict in
   `map/INDEX.md` or in a `## Children` section is resolved by running
   `index` again; two entries added to one topic by two sessions are both
   kept, newest first. Then `check`, commit the merge, push. Any other
   conflict, or a push that fails, leaves the commit local (`git merge
   --abort` when a merge is open), and the reply says
   `Map not pushed: <why>; the next push carries it.` The next round's push
   carries it.

The round's reply is given after the push. An exchange whose last round
left the map unwritten has not happened as far as the next agent can see, so
every round commits, the last one included.

**When the corpus cannot be written**, in a session with no shell or no
access to the folder, the agent still answers, writes nothing, and says so
once per exchange: `Map not written: <why>; nothing recorded.`

Example, fictional: the first round of an exchange on advisory locks writes
`software-development/postgresql/advisory-locks/topic.md` with its new entry
at *superficial*, appends the `attempt` and the `assessment` lines to
`log/2026-10.jsonl`, runs `index`, which rewrites the `## Children` section
of `software-development/postgresql/topic.md` and one line of `map/INDEX.md`,
runs `check`, which reports nothing, and commits the four files as
`Nex Colab: Advisory locks in PostgreSQL`.

## (use colab): the map in other work

The map is needed most when an agent explains something technical in the
middle of other work, a review, a fix, the cause of a failing build, so that
it knows the owner's experience in the field. The owner asks for that by
writing the phrase `(use colab)` anywhere in a message, or by calling
`/use-colab`. Nothing else starts it. It lasts for the work that message asks
for: a later message that goes on with that work is a round of it, as in an
exchange, and a message about other work ends it. The map changes how the
work is explained, never what the work is.

1. **The subagent.** When the work will write (step 3), run `index` first.
   Then hand the message to a subagent, a second agent with a context of its
   own, so that the map's files do not crowd the work: in Claude Code the
   Agent tool with the subagent type `Explore`, which cannot write; in Codex
   the tool `spawn_agent`. The agent itself reads no file of `map/` or
   `log/` in such work: it reads the brief. Give the subagent this request,
   with the corpus and the owner's whole message filled in:

   ```
   Read the Nex Knowledge Map for another agent, and write nothing: no file, no log line, no commit.
   Corpus: <corpus>
   Message: <the owner's message>
   1. Read <corpus>/map/INDEX.md. Match the subjects of the message against the titles, the aliases and the paths, and find the topics the message touches and the topics an explanation of them needs. For each path listed under "## Not interested" in the message's field, read its topic.md for its title and aliases.
   2. Read the topic.md of each topic found: its level, entries, gaps, notes and former paths.
   3. Read the lines of <corpus>/log/*.jsonl that name its path or one of its former paths since its newest entry: lines whose "at" is later than the assessment or statement line that wrote that entry; for an entry the owner made by hand, the lines from the day after its date; for a topic with no entry, every line.
   4. Answer with the brief only, one line per topic, leaving out a part with nothing to say:
      <title> (<path>) · <level, or not assessed> · gaps: <gaps> · notes: <what matters for pitching> · shown <n> times since its level was set
      where <n> counts the distinct "session" values of those "attempt" lines. Then, when the message touches a marked topic, one line: Not interested: <paths>
   ```

   Fictional example of a brief:

   ```
   Test fixtures (software-development/testing/fixtures) · superficial · notes: met fixtures only in passing · shown 1 times since its level was set
   Event loops (software-development/concurrency/event-loops) · practical
   ```

2. **The work, pitched by the brief.** Do the work as asked, and pitch every
   explanation in it as [step 3](#step-3-the-depth) says: skip what the owner
   knows, explain what they do not one level up, and close each explanation
   with the skipped line. Fictional example: `(use colab) why does this test
   hang?`; the brief has test fixtures at *superficial* and event loops at
   *practical*; the agent finds the cause, a fixture that never closes its
   loop, explains how a fixture's teardown runs and why this one never reaches
   it, without saying what an event loop is, and ends with
   `Skipped: event loops (practical).` A topic the brief marks not interested
   is used plainly, with the `Not interested:` line when the message touches
   it, and recorded nowhere.
3. **Writing, by default.** The work writes the map as an exchange does:
   each reply that explains something writes its `attempt` line (step 5),
   the assessment runs after each reply of the owner's (step 6), and the
   writes, the commit and the push follow step 7, with the lines of
   [The lines the owner sees](#the-lines-the-owner-sees): each change of
   level is its one-line `Map:` line, and such work gives no quiz, no
   marking and no list of changes, which close the replies of an exchange and
   of learn mode only. Two things make it only read:
   - *The owner says so.* Words in the message such as
     `(use colab, read only)` or "only read my map" make the work read only;
     words such as "update my map" make it write. The owner's word overrides
     the agent's own choice. Only words about the map count: "read the
     files", "don't run anything" or "just look" are about the work, and the
     work still writes.
   - *The session is already long.* When the owner has said nothing, and the
     tool shows that the session has used more than half of its context
     window, the agent puts the work in hand first and only reads. When the
     tool does not show it, the work writes.

   Work that only reads runs no `index` and writes nothing to the map or the
   log, and says so once per session, first among its `Map` lines:
   `Map read only: <why>; nothing recorded. Say "update my map" to record.`
4. **Talking a level through** works here too, one question at a time, as
   step 6 says. While the work only reads, the answer steers the explanation
   and is not recorded.
5. **A showup in the middle** of such work is handled as one in the middle of
   an exchange: it is recorded as [showup](#showup) says, its messages are no
   evidence, and the work goes on with its explanations pitched at the new
   level. A showup that names no topic, "advanced in this", refers to the
   topics of the work's last `attempt` line, or, when the work only reads, of
   the brief. A request in plain words to record a level gets the
   `To record it:` line here too.

## showup

`/colab showup "<words>"`, in Codex `$colab showup "<words>"`, is the owner
telling the agent on purpose what they know, so that the map records it as
theirs ([CLB-2](../../colab/specs/02-showup.md)). It may come at any time,
with no exchange open, in the middle of one, or in `(use colab)` work.
Nothing else is a showup:

- A request in plain words, "note in my map that I know event loops well",
  gets the `To record it:` line and writes nothing.
- A remark in passing, "I have used asyncio for years", is a claim:
  [step 1](#step-1-the-prompt) takes it as the starting value and writes no
  entry for it.

A showup shows the owner nothing and assesses nothing. It writes only what the
words give: the owner's entries, gaps, marks and aliases, the topics it has to
create for them, and the log lines below. No notes, no related links, no entry
of the agent's own, no `attempt` and no `assessment` line.

A showup takes these steps, as CLB-2's "A showup from start to end" gives
them. Fictional example, used through this section: on a map where
`software-development/databases/postgresql` stands at *superficial* from an
agent's estimate, the owner writes
`/colab showup "Six years of PostgreSQL in daily work: queries, schema design, a few index tunings. Never touched replication. Not interested in PL/pgSQL."`

### showup step 1: the topics

Run `index` before reading anything of the corpus, then read `map/INDEX.md`
once, and match each subject of the words against the titles, the aliases and
the paths. `map/INDEX.md` lists a marked topic by its path only, under
`## Not interested`, and nothing under it: read the `topic.md` of each path
listed there in the field the words name, for its title and aliases. Before
writing to any topic, read its own file and its ancestors' for the mark.

- **An existing topic** is used, also under another of its names: "Postgres"
  finds the topic titled "PostgreSQL" through its alias. A name the owner uses
  that the topic's title and aliases lack, compared without regard to case,
  is added to its `aliases`: "Go generics" for a topic titled "Generics in
  Go" is such a name.
- **A new topic** goes under the parent the words' own nesting names,
  "the actors in Swift concurrency", or under the one you judge right, with a
  `topic.md` holding only `title` for every folder on the way. A new field at
  the top of `map/` is a choice for the question (step 4), with the field you
  propose.
- **A part of a topic** the words name as not learned is step 3's.
- **Words about a particular repository, project or product**, "I know the
  billing service of one shop inside out", record nothing as they stand.
  When you see a general topic behind them, restate the words in general
  terms and offer that restatement as a choice in the question; record only
  what the owner accepts. When you see none, the reply says the subject is not
  recorded.
- **Words that name no topic**, `/colab showup "advanced in this"`: in the
  middle of an exchange they refer to the topics of the exchange's last
  `attempt` line, and when it names more than one, which of them is the
  question. Outside an exchange they record nothing, and the reply says so.

### showup step 2: the level

- **A level named by its name** is recorded as named: "practical in Swift
  concurrency" is *practical*. "Approximately", "roughly" and "about" change
  nothing.
- **Otherwise** the level is the highest whose test the words meet, by the
  tests of [step 6](#step-6-the-assessment) and no other rule. Years of
  everyday work with a topic meet *practical*, whatever the number of years;
  words that say nothing about why it behaves as it does, its limits or its
  trade-offs do not meet *advanced*. "Never heard of it" and "know nothing
  about it" are *ignorant*; "have read about it, never used it" is
  *superficial*; "could build one" is *design*.
- **Words that meet one test and hint at the next**, "reasonably well",
  "quite good at": the level is talked through with the owner, not picked
  from two (step 4).

The owner's word is the starting value, not a floor: a later exchange may
write an agent's entry above or below it, by the tests, as
[Lowering a level](#step-6-the-assessment) says. A showup that states the
level the map already shows is recorded too: the owner confirmed it that day.

In the example, "six years of PostgreSQL in daily work: queries, schema
design, a few index tunings" meets *practical* and says nothing of why
PostgreSQL behaves as it does: *practical*, with no choice.

### showup step 3: children, parts not learned, and marks

- **A statement about a topic says nothing about its children or its
  parent.** "advanced in Swift" writes to `swift/` only and leaves
  `swift/concurrency` as its own file has it; "I know nothing about actors in
  Swift" writes to the child only.
- **A part named as not learned**, "never touched replication", meets
  *ignorant*, or *superficial* when the words show the owner knows what it is
  for; when both fit, that is a choice. When the topic has no child of that
  name, the part becomes a gap on the topic, not added twice. When a child of
  that name exists, the child gets an entry at that level.
- **A clear word of not interested**, "not interested in", "do not teach me",
  "leave out", sets `not-interested: true` on the topic, created with no entry
  when the map lacks it. Words that only lean that way, "I do not care much
  about", are a choice, with the mark proposed.
- **"Interested after all"** removes the mark from the topic that carries it.
  When the mark sits on an ancestor, removing it would bring the ancestor's
  other children back too: that is a choice, proposed not to remove it.
- **A topic under a mark**, its own or an ancestor's, gets nothing: no entry,
  no gap, no alias, no topic under it. The reply names the topic that carries
  the mark; the owner removes it and states the level again.
- **A level and a mark in the same words**, "practical in PL/pgSQL but not
  interested in it": the entry is written first and the mark after it.

### showup step 4: asking back

Ask before writing anything when the words leave a choice, and only then:
two topics fit a subject; two parents fit a new topic, or it is a new field;
two adjacent levels fit the words; the words lean towards not interested; the
words name a particular product and you see a general topic behind them;
"interested after all" meets a mark on an ancestor; or words that name no
topic meet an `attempt` line with several. Ask nothing the words have settled,
and nothing about a topic the words do not name. The question is the whole
reply, one message that begins with `Before I write:`, with nothing before
it, and every choice numbered on one line:

```
Before I write:
1. Where does Tokio go? As a new topic under rust/ (proposed), or under a new rust/async-runtimes/.
2. Rust: "reasonably well" meets practical, a routine task done alone, and may meet advanced, knowing why it behaves as it does and when not to use it. What have you built with it, and could you say when Rust is the wrong choice?
Answer 1 by number or "go"; tell me about 2 in your own words.
```

The question ends with its answer line, word for word but for the numbers,
and nothing comes after it: no explanation, no reference to this guide.
`Answer 1 by number or "go"; tell me about 2 in your own words.` when it holds
both kinds of choice, `Answer 1 by number or "go".` when it holds no level,
`Answer 1 in your own words.` when it holds only levels.

- **A choice of place, field, mark or restatement** gives its options with
  the proposed one marked `(proposed)`. The owner answers with the number and
  the option they want for each choice they change, or with `go`, which takes
  every proposal; a choice they leave unnamed takes its proposal. Silence
  writes nothing.
- **A choice of level** opens a conversation, a message at a time: say in a
  sentence each what the two tests ask, and ask what the owner has done or
  can do that bears on them, as a colleague would. Show nothing and explain
  nothing: an owner who wants something explained has an exchange for it.
  Go on while the answers add something. Then name the level whose test the
  owner's words met, with that test, and ask the owner to agree:
  `That meets practical, a routine task done alone, and not yet advanced. I will record Rust as practical. Right?`
  The owner's agreement, or the level they name instead, settles it. Write
  nothing before that.
- **A message that turns to something else**, "run the tests", ends the
  showup with nothing written. The reply's first line says so, word for word:
  `Showup stopped: nothing recorded; /colab showup starts it again.`, and then
  the reply does what the message asks.
- **New words about another topic** in an answer, "and I know Diesel too",
  are a new showup, taken after the first is written.

### showup step 5: writing the topics

When every choice is settled, for each topic, read its file immediately before
writing it back whole, once, and note the level it held then, for the reply.

- **The entry.** For each topic the words give a level, one entry at the top
  of `entries`, and `level` follows it:

  ```
    - level: practical
      source: owner
      date: 2026-10-21
      evidence: "showup: Six years of PostgreSQL in daily work: queries, schema design, a few index tunings"
  ```

  `date` is the UTC date of the write, never a date the words mention.
  `evidence` begins `showup: ` and gives the sentences of the owner's words
  that bear on this topic, as given or as accepted, one or two sentences on
  one line, in double quotes with `"` and `\` escaped. Words about a subject
  not recorded never go into it.
- **Gaps, aliases and marks** go into their keys as step 1 and step 3 say.
- **A new topic** gets its folder and a `topic.md` with its `title`, and the
  entry or the mark the words give it. A child created under a topic removes
  the gap of that topic whose hyphenated form is the child's folder name.

### showup step 6: the log

Append, each in one write, as [step 7](#step-7-writing-the-map-and-the-log)
of an exchange does:

1. **One `added` line** when the showup created topics: `topics` every path
   created, the folders on the way included, and `reason` a sentence that
   begins `the owner's showup`.
2. **One `statement` line** for the whole showup, not one per topic: `topics`
   every path it wrote to, an entry, a gap, an alias or a mark; `said` the
   owner's words that bear on those topics, from the showup and from the
   conversation that settled it, as given or as accepted, leaving out words
   about a subject not recorded; `level` the new level of each topic that got
   an entry, path → level, and `{}` when none did.

```
{"at":"2026-10-21T08:14:01Z","kind":"added","session":"claude-code <session>","topics":["software-development/databases/postgresql/pl-pgsql"],"reason":"the owner's showup: created to carry the not-interested mark"}
{"at":"2026-10-21T08:14:02Z","kind":"statement","session":"claude-code <session>","topics":["software-development/databases/postgresql","software-development/databases/postgresql/pl-pgsql"],"said":"Six years of PostgreSQL in daily work: queries, schema design, a few index tunings. Never touched replication. Not interested in PL/pgSQL.","level":{"software-development/databases/postgresql":"practical"}}
```

A showup that changed nothing writes no line.

### showup step 7: finishing

Run `index`, then `check`, and commit and push as step 7 of an exchange says,
with the subject `Nex Colab: showup of <the titles of the topics written>`:
the titles joined by commas, never the owner's words, such as
`Nex Colab: showup of PostgreSQL, PL/pgSQL`. An error `check` reports in a
file the showup wrote is fixed before the commit; an error in another file is
named in the reply and left. A showup that changed nothing commits nothing.

### showup step 8: the reply

The reply says exactly what went into the map, and nothing else: it explains
nothing of the topic and offers no teaching, way deeper, quiz or list of
changes; its lines below are the record.

```
Recorded on 21 October 2026:
- software-development/databases/postgresql · practical · was superficial (agent, 2026-10-02) · gap added: replication
- software-development/databases/postgresql/pl-pgsql · not interested · new topic
```

The reply is this first line and the lines under it, and nothing else, also
when nothing was recorded. The first line names the UTC date of the write, as
`date -u '+%-d %B %Y'` prints it, never the local date. Then one line per topic
that got an entry, a gap, an alias or a mark, in this form, the parts that do
not apply left out:

```
- <path> · <level> · new topic | was <level> (<source>, <date>) · gap added: <gap> | gap removed: <gap>
- <path> · not interested | mark removed · new topic
- not recorded: <subject> · <why>
```

`was` names the level the file held at the read before the write, with the
source and date of its newest entry. One `not recorded:` line per subject the
showup did not record, with why: it names a particular product, it lies under
the mark of `<path>`, or the words name no topic.

### A showup in the middle of an exchange

Complete the showup first: the question when there is one, the writes, the
log, the commit and the push, the reply. Its messages are no rounds of the
exchange: they show nothing, write no `attempt` line, and are no evidence for
the exchange's assessment. Then go on with the exchange: read again the files
of the topics the showup changed, pitch what you show next at the new level,
and close it with the skipped line, which says what you now skip. What you
show after the showup, in the same reply or the next, is a round, with its
`attempt` line and its own commit, and closes with the quiz, the list of
changes and the ways deeper. A mark set on the topic being explained
ends that explanation. In `(use colab)` work the same holds, and words that
name no topic refer to the work's last `attempt` line, or to the brief when
the work only reads.

### What the agent never does in a showup

- Write an owner's entry without `/colab showup`, or take a plain-word
  request or a remark in passing for one.
- Write a level the words do not give, a level higher than they meet, or a
  level to a child or a parent the words do not name.
- Write before every choice is settled, or on silence.
- Write notes or related links, an entry of its own, or an `attempt` or
  `assessment` line.
- Write anything to a topic under a mark, or create a topic under one.
- Write anything that names a particular repository, project or product, in
  an entry, a `said`, a topic or a commit subject.
- Explain the topic or offer teaching in the reply.

## Learn mode

Learn mode is a whole Chat Session in which the owner only learns, toward a
goal of their own, such as getting ready for a job interview, and the agent
only teaches. It starts with `/learn "<goal>"` or `/learn` and lasts until
the owner says to leave it. Its rounds are the rounds of an exchange, steps 1
to 7 above, with four differences: it lasts the whole session; it does no
other work, also when asked; each reply gives one piece to learn; and the
options at its end are ways to go on learning in any direction, not only
deeper. There is no study plan: the agent gives a piece, offers ways on, and
reads from the owner's replies and quiz answers what they have learned, as an
exchange does, and each reply that teaches closes as an exchange's does, with
the quiz, the list of changes and the options
([CLB-3](../../colab/specs/03-learn.md)).

### What the agent may do in learn mode

From `/learn` until the owner says to leave the mode, and only this:

- **Write** files only under the corpus's `map/` and `log/`, as step 7 does,
  and git's own files of the corpus. No file anywhere else: no code written
  to a file, no project created, nothing changed in the folder the session
  started in or in any repository.
- **Run** only the commands this guide gives for the corpus: finding the
  corpus folder, `date -u`, appending a log line, `knowledge_map.py index`
  and `check`, and `git` on the corpus (`status`, `add`, `commit`, `pull`,
  `push`, `rev-parse`), and commands that only read the corpus, such as
  `cat`, `tail` or `grep` on its files. Run no build, no test, no program, no
  installer, and no code to try out what a reply shows, not even in a
  temporary folder.
- **Invoke** no skill but `learn` and `colab`, and follow no other skill's
  instructions, however close its subject is to what is being learned. A
  fact comes from public documentation.
- **Read** only the corpus, this guide and the skill, public documentation to
  check a fact before teaching it, such as a limit or a default that changes
  between versions, and a file the owner names by its path or pastes into a
  message to study. Such a file is read as step 1 reads something in the
  current session: as the example of a general topic, which is all the map
  and the log record. Never read a repository or a project's files on your
  own, the folder the session started in included.
- **Send** nothing that describes the owner: a search holds the general fact
  sought, never the goal, a level or a name the goal held.

Code may appear in a reply as part of an explanation, a few lines that show
the idea, never in a file and never run.

### Learn mode step 1: the start

**`/learn "<goal>"`** starts the mode on the goal, the owner's words: what
they want to be ready for, and often the topics they name. The message is
the first round of the mode's exchange, as `/colab "<prompt>"` is, with the
goal as its prompt: step 1 finds its general topics, step 2 its topics in
the map, and the reply gives the first piece of it, as step 2 of learn mode
below says. The goal is kept by the session only: it steers which piece
comes first and which ways are offered, and is written nowhere. A goal that
names an employer, a team or one product's insides, "prepare for the
interview at Example Corp, on their ingest pipeline", is taught through its
general topic, ingestion pipelines; the employer goes into no topic, entry,
log line or commit subject. A goal with no general topic behind it gets the
`Not a map topic:` line, and the mode does not start.

**`/learn` alone** starts the mode with no goal. Run `index`, read the last
`attempt` lines of the newest file of `log/`, and reply with the line
`What would you like to learn?` followed by the options under their title
`### Do you want to proceed with...`: the topics those lines name, the most recent first, each as an option in the
form of step 4, pitched one level above the level the map shows for it. The
reply teaches nothing, writes nothing and holds no quiz; the owner's answer, a number or
words, is the first round. With no `attempt` line in the log, the line stands
alone, without options.

### Learn mode step 2: every round

Every message in the mode that asks to learn something, or answers what the
agent taught or asked, is a round: steps 2 to 7 of an exchange. What changes:

- **One exchange for the whole mode.** All the rounds of learn mode in one
  session are one exchange: step 6 assesses every topic the mode has
  touched, from everything the owner said since `/learn`; words that only
  restate what the mode has shown are no proof; `Map check:` and
  `Map not written:` are said once in the mode; a showup that names no topic
  refers to the mode's last `attempt` line. The `Shown` line counts
  exchanges by session, as step 6 says.
- **Nothing ends it but the owner's word.** A message off the topics of the
  last round, on any general topic, is a round too, and so are a number from
  the last options, the answers to the last quiz, an objection to the skipped
  line, a request for code a
  reply can show, `/colab "<prompt>"` and `/colab showup "<words>"`. Only
  what [Leaving](#learn-mode-step-4-leaving) says ends the mode.
- **One piece per reply.** The reply gives one piece to learn, not all that
  the depth table of step 3 names at once: a part of what the owner should
  learn next, sized to be read in one sitting, pitched one level above the
  level the map shows, by the table. A topic not assessed is pitched as new
  to the owner, with the skipped line saying so. The rest of the topic is
  among the ways on.
- **The quiz and the list of changes** close every reply that teaches, as
  step 4 and step 6 say: the quiz on the piece just given, two to four
  questions for one piece as a rule, then the list when the round changed the
  map. The answers to the quiz are a round: the next reply marks them first,
  after only a `Learn mode is on:` line, and a reply that only marks ends
  with the options.
- **The ways on.** The reply ends with options, after the quiz and the list of
  changes, as step 4 says, in its form,
  `<n>. <the way> (<topic>, toward <level>)`, a few, the most useful first,
  none into a marked topic, and none taken before the owner answers. They
  are the ways to go on learning, not only the ways deeper: the next piece of
  the same topic, a child, a gap, the topic's next level, a related topic, a
  sibling under the same parent, another topic the goal named, or anything
  else that fits the goal and what the owner has just shown. Which ones is
  your judgement; at least one way should lead away from the topic just
  taught, so that the owner can change direction with one number.
- **Always written.** The map and the log are written in every round, as
  step 7 says, also in a long session: the rule of `(use colab)` work that
  only reads in a long session does not apply.

The question that talks a level through may stand before the quiz, as step
6 allows. Besides the quiz, ask no practice question with a model answer and
run no mock interview: the owner decided that learn mode has none.

### Learn mode step 3: a request for other work

A request is *other work* when answering it needs something learn mode does
not do: a file written or changed, a command run, a repository or a project
read for what it does, an outside system touched. "Write this consumer to a
file", "run the tests", "what does our pipeline's retry setting do?". The
owner decided that learn mode is never mixed with real work: other work is
not done, and the mode does not end. The reply is the line

```
Learn mode is on: <the work asked, in a few words> is not done here; say "leave learn mode" to end it.
```

followed by the options to go on learning, the general topic behind the
request among them when it has one. It shows nothing, writes nothing,
commits nothing, and holds no quiz and no list of changes. When the same
message also answers the last quiz, the marking follows the line, the
answers are assessed and written as in any round, and the list of changes
follows the marking when they changed the map. A request a reply can satisfy is learning, not work: "show
me in code how a consumer commits its position" is answered with the code in
the reply.

### Learn mode step 4: leaving

Only the owner's word ends the mode: any words that say to end or leave
learn mode or to stop learning, "leave learn mode", "stop learning", "that
is all for today, end learn mode". The reply is the line

```
Learn mode ended; /learn starts it again.
```

and nothing more: answers to the last quiz in the same message are not
marked and change nothing. When the same message also asks for work, "leave learn
mode and fix the failing test", the reply begins with that line, and the
rest of the message is answered as it would be without learn mode. The mode
also ends when the session closes.

### What the agent never does in learn mode

- Write, change or delete a file outside the corpus's `map/` and `log/`;
  write code to a file; change the folder the session started in or any
  repository.
- Run a build, a test, a program, an installer, or code that shows what a
  reply explains; run any command that writes outside the corpus.
- Invoke or follow a skill other than `learn` and `colab`.
- Read a repository or a project's files that the owner did not name or
  paste to study.
- Do other work, or end the mode, on a request for work alone.
- Ask a practice question with a model answer or run a mock interview; the
  quiz of step 4 is the one set of questions.
- Write the goal, or any employer, product or repository it names, into the
  map, the log or a commit subject.

## The lines the owner sees

A reply holds them in the order of this table, each in its form, each line
starting with the word given; each of the three closing blocks is its title,
a third-level Markdown heading, a blank line and its lines, as step 4 shows.
`<topic>` is the topic's title,
`<level>` one of the five levels. The forms are exact: only the parts in
`<…>` are filled in, and nothing is added to a line, so `Skipped:` names
topics and levels and nothing else. A line whose *When* does not hold is left
out: the list of changes, or a `Map:` line in `(use colab)` work, is written
only for a change the round made, and when nothing changed there is none. The
reply says nothing else about the map: no account of what was written,
checked, committed or pushed beyond the list of changes, no `Shown` line below
three exchanges unless the owner asked, no sentence about a line that is left
out, such as why there is no `Shown` line or no quiz, and no advice about
showup beyond the lines of this table. A length the owner asks for, "in two
sentences", is the length of the explanation; the lines of this table come on
top of it.

| Line | Form | When |
|---|---|---|
| Learn mode ended | `Learn mode ended; /learn starts it again.` | the whole reply to the owner's word to leave learn mode, or first when the message also asks for work |
| Learn mode, other work | `Learn mode is on: <the work asked, in a few words> is not done here; say "leave learn mode" to end it.` | first in the reply to a request for other work in learn mode, followed by the options |
| Learn mode, what to learn | `What would you like to learn?` followed by the options under their title | the reply to `/learn` alone |
| The marking | `Quiz answers: <right> of <questions> right.`, then one line per question of the last quiz, in its order: `- <n><letter>: right.`, `- <n><letter>: wrong; <letter>) <the right option>: <why, in a few words>.` or `- <n>: not answered.` | first in the reply to a message that answers the last quiz, after only a learn mode line |
| To record it | `To record it: /colab showup "<the words>"` | when the owner asks in plain words to record a level; nothing is written for it |
| Not interested | `Not interested: <topic> is marked; it is answered without the map and nothing is recorded for it; showup removes the mark.` | at the start of the reply, for a touched topic that is marked |
| Not a map topic | `Not a map topic: <what the prompt is about>; answered without the map, nothing recorded.` | at the start of the reply, for a prompt with no general topic |
| The explanation | free text, pitched as step 3 says | |
| The skipped line | `Skipped: <topic> (<level>), <topic> (not assessed).` or `Skipped: nothing.`; for a touched topic with no entry and nothing in the prompt's words the period gives way to `; pitched <topic> as new to you, say so if not.`; for a level the owner only claimed, to `; pitched <topic> at <level>, as you said.` | after the explanation of every reply that explains a topic by the map |
| Read only | `Map read only: <why>; nothing recorded. Say "update my map" to record.` | first among the `Map` lines of `(use colab)` work that only reads, once per session |
| A change of level, in `(use colab)` work | `Map: <topic> <before> → <after>: <the test met, in a few words>.`; for a first entry `Map: <topic> → <level>: <the test met>.` | in the round of `(use colab)` work that wrote the entry |
| A level below the owner's own entry, in `(use colab)` work | `Map: <topic> <before> → <after>, re-evaluating your own entry: <the gap, in a few words>; showup restates it.` | in the round of `(use colab)` work that wrote the entry |
| A check error elsewhere | `Map check: <file>: <message>; left as it is.` | after `check`, once per exchange for one file |
| Not pushed | `Map not pushed: <why>; the next push carries it.` | in the round whose push failed |
| Not written | `Map not written: <why>; nothing recorded.` | once per exchange, when the corpus cannot be written |
| Shown without a rise | `Shown in <n> exchanges since <level>: <topic>; say where you stand (/colab showup), or ask for it another way.`; for a topic with no entry `Shown in <n> exchanges, never assessed: <topic>; say where you stand (/colab showup), or ask for it another way.` | in the round that makes it the third exchange or a later one, or when the owner asks to be reminded |
| A question that talks a level through | one open question that invites the owner to reason with the topic | before the quiz, when the owner's words sit between two levels' tests |
| The quiz | the title `### Quiz`, the line `Answer as 1b 2d 3a, or skip it.`, then each question as `<n>. <the question>`, numbered from 1, with its four options under it as `   - a) <option>` to `   - d) <option>` | in every reply of an exchange or of learn mode that writes an `attempt` line, 2 to 10 questions |
| The list of changes | the title `### Learnings`, then one line per topic: `- <topic>: <before> → <after>: <the test met, in a few words>.`, `<before>` being `not assessed` for a first entry and `new topic` for a topic the round added; `- <topic>: <before> → <after>, re-evaluating your own entry: <the gap, in a few words>; showup restates it.` when it replaces the owner's own entry; `- <topic>: new topic → not assessed: <why it was added, in a few words>.` for a topic added without an entry | after the quiz, in a round of an exchange or of learn mode that changed a level or added a topic |
| The options | the title `### Do you want to proceed with...`, then `<n>. <the way> (<topic>, toward <level>)`, one line per way | last, one per way deeper; in learn mode one per way to go on learning; after the `Learn mode is on:` line and the `What would you like to learn?` line too |

## What the agent never does

- Read or write the map without the owner's `/colab`, `(use colab)`,
  `/use-colab` or `/learn`, or write the owner's map in a trial or a sample, which point
  the agent at a fictional corpus with `COLAB_CORPUS`.
- Write a level from what it showed, from the number of rounds, from how
  long the owner has used something, or from a claim alone; or write a level
  to a child from its parent, or to a parent from its children.
- Delete or change an entry, whoever made it; delete or move a topic; edit
  `map/INDEX.md` or a `## Children` section by hand; rewrite or remove a log
  line, or write one with other keys than its kind's.
- Set or remove a not-interested mark on its own judgement, or write anything
  for a marked topic or under it.
- Take a way deeper the owner did not pick.
- Raise a level on a quiz unless every question on the topic was answered
  right, at least two; lower one for a wrong answer; or give a quiz, a
  marking or a list of changes in a showup's reply or in `(use colab)` work.
- Write a topic, a note, an evidence, a `shown` or a `reason` that names a
  repository, a project or a product, the owner's own included.
- Quote the map or the log outside the owner's session.
- Commit files the round did not write, commit when git's top folder is not
  the corpus, set an identity, or add an agent credit; amend a commit, force
  a push, or rewrite the corpus's history in any other way.
